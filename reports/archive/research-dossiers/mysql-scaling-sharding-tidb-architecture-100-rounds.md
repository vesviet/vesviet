## 1. Executive Objective & Synthesis

### Objective
Exhaustive 100-round deep empirical research investigating MySQL vertical scaling limits, MySQL 8.4 LTS upgrade paths, Vitess and Citus sharding middleware, TiDB 8.1+ Multi-Raft NewSQL distributed architecture, sharding key skew mitigations, and online schema migration engines (gh-ost vs TiDB distributed DDL).

### Key Architectural Findings
- **MySQL single-instance scalability hits a structural latency cliff when InnoDB working dataset exceeds physical RAM buffer pool, causing B+ tree depth to reach 4+ and I/O wait to dominate query latency.**
- **MySQL 8.0 reaches official Premier Support End-Of-Life (EOL) in April 2026, compelling enterprises to evaluate in-place upgrade to MySQL 8.4 LTS versus architectural re-platforming to Distributed SQL.**
- **Vitess middleware delivers horizontal OLTP scale via VTGate proxies and VSchema keyranges, but imposes severe cognitive toil, cross-shard 2PC latency penalties, and limited distributed transaction ergonomics.**
- **TiDB 8.1+ NewSQL combines a stateless MySQL-compatible SQL compute layer with a Multi-Raft distributed transactional key-value store (TiKV) and real-time columnar engine (TiFlash), eliminating manual resharding entirely.**
- **For online schema changes, gh-ost eliminates trigger contention via asynchronous binary log streaming, whereas TiDB implements non-blocking distributed online DDL based on the Google F1 state machine protocol.**

### Forward Inferences (2026–2027)
- Enterprises maintaining legacy MySQL 8.0 instances past April 2026 will face steep extended support surcharges and operational compliance risks, accelerating NewSQL migrations.
- The historical tradeoff between MySQL transactional stability and horizontal scaling will dissolve as Multi-Raft NewSQL engines mature in cost-efficiency and cross-datacenter resilience.

### Critical Production Gaps & Mitigations
- Cross-availability-zone network round-trip time (RTT > 1.5ms) introduces measurable commit latency in Percolator 2PC models under write-intensive bursts.
- Vitess dynamic resharding (`Reshard` workflow) requires strict operational monitoring during shard splits to prevent replication lag thundering herds on downstream consumers.
